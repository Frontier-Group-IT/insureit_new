# AI Policy Onboarding — issuance evidence, automatic customer choice and genuine exceptions

Status: **proposed production repair, not yet deployed.** Synthetic regression only; live-only Supabase remains unchanged until a reviewed merge/migration. Existing customers, policy bookings and saved Intake drafts are never overwritten by this PR.

## Verified causes (2026-11-17)
- The **active** n8n ICICI Product 3005 parser already returns `policy_issuance_date` when an explicitly labelled PDF issue date exists. However `policy-intake-n8n-validation.ts` rejected this field as unknown, while `preparePolicyIntakeHandoffInternal` always filled `issuanceDate` with today's UTC date even for a validated n8n source. As a result the form could look 100% complete while showing a date not evidenced by the PDF.
- Among 175 classified exceptions in read-only production inspection: all had an issuance-date exception and bundled-validity exception; 172 had a synthetic reviewer-status conflict; 171 were flagged for shared phone/different name. These tags overlap and do NOT prove 175 policies were invalid.
- The pure classifier flagged any bundled policy as invalid (`bundledPeriodsVerified=!bundled`) even after the strict 13 checks. It treated every Intake not already `in_review` as a reviewer conflict, and required manual customer onboarding for a different insured on the same phone, contrary to existing policy creation's `createNewCustomer` mechanism.
- The existing n8n queue also contained already-known policy number duplicates: at investigation, a read-only canonical normalized policy-number comparison found 111 already-unsupported, 22 exception, and 1 failed queue entries also duplicate-matched. Duplicate records must remain in history but never consume additional PDF extraction capacity.

## Code repairs
1. n8n's **separately printed** `policy_issuance_date` is added to the strict server allowed field contract, with exact valid ISO date validation. It is **optional** because a policy without independent issuance evidence must not invent a date from cover start or the current clock. When the PDF explicitly supplies one, new verified onboarding drafts prefill **that exact date**. Existing saved nonblank operator dates are never replaced; empty saved draft dates may be filled with explicit action.
2. For bundled ICICI 3005, independently validated OD and TP dates no longer create a generic exception. OTP eligibility is calculated from the actual verified issuance date using the existing India-calendar rule. A genuine old-month OTP, missing issue date, changed PDF, premium mismatch, duplicate, master ambiguity or ownership/coverage conflict still requires review.
3. Same phone plus a **different PDF-verified insured name** is treated as the standard create-separate-customer flow, not a conflict. Exactly one existing same-phone/same-name customer can be selected, zero exact matches leads to the canonical `createNewCustomer` transaction, and two or more exact matches remain ambiguous. This decision is never inferred solely from a matching phone.
4. The AI queue separates `verified` (PDF extraction complete, not yet booking permission) from `exception`, `duplicate` (skip n8n) and `unsupported`. Unverified preflight is a workflow step, not an extraction error. Workbench counts and labels distinguish **PDF extracted**, **actual exceptions**, and **duplicates skipped**; the bulk conversion button stays locked until a full server-owned automatic conversion job exists.
5. New custom-confirmation **Convert to Policy** per-row action invokes `convertVerifiedAiIntake`. It re-extracts the current private PDF and compares its saved queue document + fingerprint; confirms exact issue date, insured name, policy number, Basic OD/add-ons/TP/CPA, OD/TP periods; claims the existing canonical Intake draft and runs `onboardPolicy` rather than direct table inserts. If no exact same-identity customer exists, it passes `createNewCustomer:true` so the existing RPC creates a separate customer with the SAME mobile, without redirecting to the Customer Onboarding page.
6. Additive private queue-only migration adds the `duplicate` state, retires existing canonically proven duplicate queue rows, re-enqueues old false-exception rows for **re-extraction** rather than assuming dates, and preserves v2 priority/lease semantics. No policy, customer, vehicle, original OCR or onboarding draft data is changed.

## Remaining step before truly unattended policy *booking*
Extraction and customer-resolution classification are unattended; this patch also enables **one-step** authorized conversion where all required evidence is present. It deliberately does **not** impersonate an Operations user or bypass old-month email OTP. Full auto-booking needs a **dedicated accountable service actor**, a separate idempotent server-owned booking queue and exact canonical conflict/date/permission checks with no client session. No safe service actor has yet been provisioned. Therefore do not label the current bulk convert or extractor as an automatically booking system; leave booking feature off until a separately approved actor and transaction-compatible job are audited. Simply removing a true date/ownership/coverage exception is unsafe.
