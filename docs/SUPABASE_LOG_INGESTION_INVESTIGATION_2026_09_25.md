# Supabase Log Ingestion Investigation — 2026-09-25

Status: INVESTIGATION ONLY — no production logic, security rule, permission rule, or database schema has been changed by this investigation.

## Why this investigation exists

Supabase Usage showed the current organization on the Free Plan with Log Ingestion at approximately **3.32 GB / 1 GB (332%)** for the billing cycle **09 Sep 2026 – 09 Oct 2026**.

The goal of this investigation is to identify the real contributors with evidence before optimizing anything, so we can reduce consumption surgically without weakening authentication, authorization, route protection, or business functionality.

## Executive conclusion

There are two different stories:

1. **The dominant billing-cycle baseline problem is authorization/request amplification.**
   - Across 09 Sep through the partial day on 25 Sep, the four endpoints below alone account for about **1.423 billion log-attribute characters**, roughly **40% of all Supabase Edge-log payload measured in the same windows**:
     - `/rest/v1/profiles`
     - `/auth/v1/user`
     - `/rest/v1/employee_permission_overrides`
     - `/rest/v1/role_permission_overrides`
   - The single largest endpoint over the measured billing-cycle period is `/rest/v1/profiles`.

2. **The sudden 25 Sep increase has an additional major contributor: production voice campaigns.**
   - In the latest 24-hour window, voice-campaign-related Supabase endpoints generated about **83.5M log-attribute characters**, about **23.7% of the measured Edge-log payload for that window**.
   - The largest campaign, **TATA Breaking**, had 612 campaign members but 1,298 local voice attempts, an average of 2.12 attempts per opportunity. 230 opportunities had 3 or more attempts; one reached 6.
   - This is not evidence of duplicate webhook delivery. The number of submission RPC calls and result RPC calls are effectively one-for-one with local call attempts. The amplification is mainly real additional call attempts/retries plus the normal database work around each attempt.

The current overage is therefore **not explained by one rogue user, an external attack, or database/storage growth**. It is primarily generated by normal INSUREIT application activity being multiplied into many Supabase Auth/PostgREST requests.

### Why `profiles` is the single largest endpoint

The portal resolves a profile in multiple places:

1. Middleware `checkSession()`:
   - calls `/auth/v1/user`
   - then calls `/rest/v1/profiles`
   - both with `cache: "no-store"`

2. Server rendering / server actions:
   - `getAuthenticatedProfile()` validates JWT claims and separately queries `profiles`
   - React `cache()` deduplicates within an applicable render/request boundary, but it is not a durable cross-request authorization cache

3. Customer/mobile flows also read `profiles` directly.

Therefore the same human navigation can cause:
- one middleware profile fetch
- another server-side profile fetch
- plus permission-table lookups
- plus page/business-data queries

## Permission-resolution amplification

Current implementation:

- `hasEffectiveCapability()` calls `getEffectivePermission()`
- `getEffectivePermission()` can query:
  - `employee_permission_overrides`
  - `role_permission_overrides`

A single page may check multiple capabilities. `hasAnyEffectiveCapability()` executes checks in parallel per capability.

There is also a bulk function:
- `getEffectivePermissionAccessMapForRole()`

which loads the employee and role override sets in two queries and resolves the capability map in memory.

Important: this is a security layer, not something to remove. Optimization should preserve the same effective access semantics while reducing repeated database round trips.

### Important nuance about the `retry_attempt` column

`startItSuperUserExternalRenewalVoiceAttempt()` inserts a local attempt with:
`retry_attempt: previousAttempts.length`

But the webhook result RPC later overwrites the parent attempt's `retry_attempt` with the provider payload's retry counter:
`retry_attempt = greatest(coalesce(p_retry_attempt,0),0)`

Therefore the stored `retry_attempt` column is not a reliable measure of how many local campaign attempts were made for the opportunity. Counting actual attempt rows per opportunity is the reliable metric used above.

### Attempt creation occurred in large bursts

For the 612-member **TATA Breaking** campaign, local attempt rows were created in concentrated minute-level waves between roughly 10:52Z and 11:55Z on 25 Sep. Examples include:
- 91 attempts in one minute
- 98 attempts in one minute
- 108 attempts in one minute
- 99 attempts in one minute
- 100 attempts in one minute

This matches the campaign runner's batched dispatch design and repeated queue/retry passes, rather than human users opening individual records manually.

The current runner calls `dispatch-batch` repeatedly, and each batch processes up to 3 pending campaign members. The client loops up to 40 batch requests per queueing action. For a large campaign this is expected to generate many serverless invocations and related Supabase reads/writes. When busy/no-answer members are requeued, the same machinery runs again.

The webhook result RPC also checks `provider_attempt_id` and returns idempotently when the same provider attempt was already recorded.

Therefore the evidence currently points to **real repeated call attempts/retries**, not uncontrolled provider webhook duplication.

## Most important conclusion for the next fix phase

There is not one single bug to patch.

The correct surgical plan should preserve every security guarantee and address three layers separately:

### Phase A — secure session/profile de-amplification
Goal:
- preserve immediate enforcement of disabled users / role changes / shared-browser safety
- avoid `auth/v1/user + profiles` on every protected navigation
- define a bounded, security-safe revalidation strategy rather than trusting a stale role indefinitely

Do NOT simply revert the 17 Sep security hardening.

### Phase B — permission resolution consolidation
Goal:
- resolve the full effective permission set once per request/session boundary where safe
- reuse the result for multiple capability checks
- keep employee overrides, role overrides, backoffice ceilings and IT Super User rules exactly equivalent

### Phase C — voice campaign query/retry efficiency
Goal:
- retain campaign functionality and legitimate busy/no-answer retries
- add an explicit, auditable retry ceiling/business rule
- reduce repeated campaign detail/member/opportunity reads
- avoid loading full large member/attempt datasets on every refresh where counts or paginated subsets are enough

### Later phases
- replace 2-second claim polling with a slower fallback / visibility-aware fallback around Realtime
- reduce Customer App repeated profile/context reads
- review high-cost report/onboarding pages for duplicate server-side fetching
